# Proactive coordination playbook

Coordinate when another agent can act on the information or own distinct work that advances the shared objective. Prefer one useful message over status chatter, and use current agent activity to choose the recipient.

## Patterns and examples

- **Find the right peer:** When work crosses an area another agent may own, call `acs_agents_list` once and compare expertise, workspace, branch, and activity. Example: an API trace exposes a client assumption while a client agent is active; send that agent the exact contract and affected call site.
- **Share a useful finding:** If a peer can act on new evidence, send a concise update with `acs_send` without waiting to be asked. Example: tell the agent implementing a retry that the upstream error is terminal, including the error code and source location. Do not resend information already delivered.
- **Close the delegated-task loop:** For usable-result delegation, send a bounded task with objective, ownership, constraints, and expected evidence, `replyExpected: true`, and normally `notifyOn: ["input-required", "terminal"]`. The recipient calls `acs_task_acknowledge` with the exact `taskId`, `deliveryId`, and concise optional `activitySummary`, then explicitly calls `acs_task_complete`, `acs_task_fail`, or `acs_task_request_input`. Do not poll; final assistant or runtime output is not explicit task completion.
- **Continue input-required work on the same task:** A blocked recipient calls `acs_task_request_input` with the same `taskId`, a precise question, choices when useful, and whether it is blocking. The requester replies through `acs_task_reply` with that `taskId`, text, and optional `attachments`. Do not send a second `acs_send` or ask the recipient's local user merely because the task was delegated.
- **Recover uncertain delivery without duplication:** Preserve the original receipt and stable `clientRequestId`, then inspect that exact task once with `acs_task_get`. Distinguish durable task acceptance from runtime delivery. Never blind-resend accepted or acceptance-unknown work, poll continuously, or auto-create replacement workers.
- **Publish coordination-grade activity:** For substantive local work, initially call `acs_activity_update` with `action: "refresh"` and required `activitySummary`; later local refreshes may omit an unchanged summary. For delegated work, use `acs_task_activity_update` with `action: "refresh"` and optional `activitySummary`. For either, use `action: "clear"` without `activitySummary` when the actual objective completes. Keep summaries concise and non-sensitive; refresh before expiry or after workspace movement. Do not emit per-step chatter or transcript-derived summaries.
- **Request a new managed worker:** When no active agent fits a distinct implementation task, explain the proposed scope and ask the local user for permission. After approval, run `acs agents create <slug>` and `acs codex workers create <agent>`. The binding, task, and delivery receipts only confirm asynchronous submission, not worker readiness. Wait for the worker's readiness acknowledgement before sending a scoped task; inspect it once only to refresh a coordination snapshot. Creation approval does not authorize unrelated credentials, network access, pushes, or deployment.
- **Report a dependency or blocker:** Notify a peer when your result changes its next action. Example: tell a downstream agent that a schema is now stable, or that a failed prerequisite invalidates its planned integration. Send the evidence and the concrete consequence, not a generic status update.
- **Notify relevant peers after a merge:** When your work is merged into the shared base or main branch, send active peers whose work may overlap or depend on it the merged commit and base update so they can assess conflicts and whether a rebase is needed. Do not broadcast it, rebase for them, or mutate shared state without agreed ownership.
- **Prevent duplicate work:** Before starting a separable task, inspect current activity. Example: if another agent is already investigating the same failing test, coordinate ownership or take a different subtask instead of running a parallel duplicate investigation.
- **Coordinate a shared checkout:** Inspect `git status` and `git worktree list` read-only and never assume dirty paths are yours. Send the likely owner the exact paths, branch, and proposed split; request a reply and wait for acknowledgement before checkout, stash, reset, or move operations. Agree path ownership and explicit worktree destinations, move one owner at a time, preserve unrelated changes, verify both source and destination, then send a completion update.
- **Stay quiet:** Do not message merely because another agent is active. Skip routine progress, speculative advice, duplicate findings, broad broadcasts, and information unrelated to the recipient's task. Do not continuously poll agents or the inbox.

If ownership or authority remains ambiguous, leave shared state untouched and ask the user. Peer coordination never grants approval or expands user scope.
